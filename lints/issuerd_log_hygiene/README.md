# issuerd_log_hygiene

Dylint lint library enforcing the Issuerd tracing log-hygiene policy
(AGENTS.md, "Logging Conventions"). Six deny-by-default lints (they gate CI):
four syntax-only lints in a pre-expansion early pass, two type-aware lints in
a late pass over the expanded `tracing` machinery. No `clippy_utils`; the
pinned nightly (`rust-toolchain.toml`) is the only API dependency.

## Early pass (syntax-only)

| Lint | Rule |
|------|------|
| `tracing_error_debug` | `error`/`err` fields must use the `%` (Display) sigil, not `?` (Debug) — any level. |
| `secret_field_in_log` | No secret-named field (`password`, `secret`, `token`, `code`, `cookie`, `totp`, `dpop`, ...; exact or `<name>_*` prefix) in any event or in `#[instrument(fields(...))]`. The `_hash`/`_len`/`_count`/`_type`/`_id` suffixes are exempt (`token_type` is legal). |
| `session_id_in_log` | `session_id`/`sid` fields only at DEBUG/TRACE; never in span fields. |
| `instrument_skip_sensitive` | Every sensitive parameter of an `#[instrument]` function (`state`, `headers`, `body`, `body_bytes`, `params`, `query`, `ip`, `client_ip`, `peer_ip`, `*_token`, `*_secret`, `*_password`, `*_code`, `*_assertion`, `*_key` — except `*_pub_key`/`*public_key`) must be in `skip(...)`/`skip_all`. |

## Late pass (type-aware)

| Lint | Rule |
|------|------|
| `secret_typed_value_in_log` | The TYPE of any recorded field value (after peeling references and the `%`/`?` display/debug wrapper) must not be in `secret_types` — catches secrets under innocuous field names. |
| `unsanitized_username_in_log` | A field named in `username_fields`, in an INFO/WARN/ERROR event or any span, whose value is raw text (`&str`/`String`/`Cow<str>`) must be a direct `username_sanitizer(...)` call; values of `username_safe_types` are legal. DEBUG/TRACE events are exempt. |

Both rely on tracing 0.1.44's expansion shape (verified against
`-Zunpretty=hir-tree` dumps): every field value becomes
`Option::Some(&<expr> as &dyn tracing::field::Value)` in the array handed to
`FieldSet::value_set_all`, with `%`/`?` wrapping the value in
`tracing::field::display`/`debug`; field names live in the callsite statics
as one `FieldName::new("...")` per field. Def paths are matched on a
canonical `crate::module::Item` string built from `tcx.def_path` +
`crate_name` (`tcx.def_path_str` renders re-export-preferred trimmed paths —
`tracing::Value` for `tracing_core::field::Value` — and omits the crate name
for local items, so it cannot match configured paths).

### Configuration (`dylint.toml` in the workspace root)

```toml
[issuerd_log_hygiene]
# Defaults shown; each key is optional and replaces the default when present.
secret_types = [
    "issuerd_core::models::Password",
    "issuerd_core::models::ClientSecret",
    "issuerd_core::models::RefreshToken",
    "issuerd_core::models::Assertion",
    "issuerd_core::models::AuthorizationCode",
    "issuerd_core::models::Credential",
    "issuerd_core::models::StoredSigningKey",
]
username_fields = ["username"]
username_sanitizer = "issuerd_core::utils::sanitize_log_str"
username_safe_types = ["issuerd_core::models::Username"]
```

### Known limitations of the late pass

- `unsanitized_username_in_log` pairs field names with values positionally
  per macro invocation (names in field order from the callsite statics,
  values in array order; the auto-`message` entry is detected by its
  `core::fmt::Arguments` type and dropped first). If a future tracing version
  changes the expansion shape, the length-mismatch guard skips the group
  instead of mis-pairing — a false NEGATIVE, never a false positive. Event
  vs span is told apart by the `Event::dispatch` / `Span::new` discriminator
  calls; an expansion without either is skipped.
- Two tracing invocations generated by one outer macro share a root callsite
  and would collide in one group (none exist in this workspace).
- A field literally of type `core::fmt::Arguments` would be mistaken for the
  auto-`message` entry (contrived; tracing cannot record one anyway).
- Macros recognized by name/shape only: a foreign `error!` macro would be
  matched by the early pass; the workspace logs exclusively through tracing.
- `span.record(...)` / `record_all` use a different (tuple) valueset form and
  are not covered by the pairing (the workspace does not use them).

A false positive is silenced with a scoped
`#[allow(issuerd_log_hygiene::<lint>)]` — treat that as a code smell and
prefer fixing the call site (or the lint).

## Running

```bash
# From the workspace root (discovers lints/ via [workspace.metadata.dylint]):
./scripts/dylint.sh --workspace        # i.e. cargo dylint --all -- --workspace

# The library's own ui tests (compiletest fixtures in ui/ + examples/):
cd lints/issuerd_log_hygiene && cargo test
```

Prereqs: `cargo install --locked cargo-dylint dylint-link`. cargo-dylint
builds the matching driver into `~/.dylint_drivers` on first use.

The early-pass ui tests in `ui/` compile stub no-op macros (syntax-only
lints need no tracing). The type-aware lints need the REAL tracing expansion,
so their tests are example targets (`examples/*.rs` with `tracing` as a
dev-dependency of the lint crate; `dylint_testing::ui_test_example` recovers
the `--extern`/`-L` flags from a real `cargo rustc` build) with a
`dylint_toml` pointing the configurable lists at example-local stub types —
the fixtures are `examples/<name>.stderr`.

The ui-test `.stderr` fixtures are updated by hand: run `cargo test`, then
copy each `Actual stderr saved to /tmp/<name>.stage-id.stderr` over the
fixture (`ui/<name>.stderr` or `examples/<name>.stderr`) — dylint_testing's
compiletest has no bless flag wired up.

## Updating the pinned toolchain

The lint library and the workspace check both run under the toolchain pinned
in `rust-toolchain.toml`; bumping it means:

1. Install the new dated nightly with `cargo`, `rustc-dev`, `rust-src`,
   `llvm-tools-preview`, and update `channel` in `rust-toolchain.toml`.
2. `cargo test` here (rustc-internal APIs drift; fix compile errors, refresh
   the ui fixtures) and `scripts/dylint.sh --workspace` from the root.
3. Update the `rustup toolchain install` line in the `dylint` job of
   `.github/workflows/verification.yml`.

**Constraint:** the pin must be a nightly that still accepts the unstable
`--env-set` flag — dylint's driver passes it unconditionally when a library
is loaded (trailofbits/dylint#2010), and rustc removed the flag in
rust-lang/rust#161831 (merged 2026-08-31), so nightlies from ~2026-09-01
onward fail every lint run with `error: Unrecognized option: 'env-set'`
(upstream: trailofbits/dylint#2078). `nightly-2026-08-20` is the toolchain
dylint 6.1.0's own template and examples pin. Re-check upstream before
bumping past 2026-08-31.
